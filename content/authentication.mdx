Every route on this site — pages, search, the API playground proxy, even
`llms.txt` — sits behind authentication. There is no anonymous mode.

## The flow

Sign-in is **Descope only** — there is no password form and no credential
store in this codebase. The login page embeds our Descope Flow (via the
official `@descope/react-sdk`), so the entire sign-in experience — MFA,
passkeys, magic links, social login — is configured in the Descope console
with zero code changes here.

<Steps>
  <Step title="Sign in via Descope">
    The embedded flow authenticates the user against Descope. On success the
    server validates Descope's session JWT against Descope's JWKS (signature,
    expiry, issuer) and mints the docs session.
  </Step>
  <Step title="Session cookie">
    On success the server issues a JWT (HS256, signed with `SESSION_SECRET`)
    carrying the user's email, name, and role. It's stored as an HTTP-only,
    `SameSite=Lax` cookie with a 7-day expiry.
  </Step>
  <Step title="Middleware guard">
    `middleware.ts` verifies the token on **every request**. Unauthenticated
    page requests redirect to `/login?next=…`; unauthenticated API requests
    get a `401` JSON response.
  </Step>
</Steps>

## What's protected

| Surface | Behavior without a session |
| --- | --- |
| Doc pages | Redirect to `/login` |
| Search API | `401` |
| Feedback API | `401` |
| `llms.txt` | `401` |
| Smilify API (`/api/v1/*`) | Own bearer-key auth, like any product API |

<Info>
  The Smilify API is deliberately outside the docs session wall — it
  authenticates with an `Authorization: Bearer` key, not your docs cookie,
  exactly as clients consume it in the wild.
</Info>

## Roles — managed in Descope

Docs roles come from **Descope role claims**, so access is administered in
the Descope console, not in code:

<Steps>
  <Step title="Define roles in Descope">
    Console → **Authorization → Roles** — create (or reuse) a role such as
    `docs-admin`.
  </Step>
  <Step title="Assign roles to users">
    Console → **Users** → select a user → assign the role. Changes apply on
    the user's next sign-in.
  </Step>
  <Step title="Map Descope roles to docs roles">
    Any Descope role listed in `DESCOPE_ADMIN_ROLES` (default
    `admin, docs-admin`) grants the docs **admin** role; everyone else who
    can sign in is a **member**. `DESCOPE_ADMIN_EMAILS` force-grants admin to
    specific emails regardless of roles, and `DESCOPE_ROLES_CLAIM` points at
    a differently-named claim if your tenant customizes it.
  </Step>
</Steps>

The role is embedded in the signed docs session at sign-in, then enforced in
three places: admin-only sidebar groups, direct URLs (members get a 404),
and search results (filtered server-side).

Role checks apply in three places: sidebar rendering, page access (non-listed
roles get a 404, not a 403 — the page's existence isn't leaked), and search
results.

## Configuring Descope

Set the environment variables (see `.env.example`):

```bash title=".env"
DESCOPE_PROJECT_ID=P2xxxxxxxxxxxx      # embeds the Descope flow on /login
DESCOPE_FLOW_ID=sign-up-or-in          # which flow to show
DESCOPE_ADMIN_ROLES=docs-admin         # Descope roles that grant docs admin
```

One-time console setup: add this deployment's origin to the Descope
project's **approved domains** so the embedded flow may run.

<Note>
  Changing sign-in policy — enforcing MFA, adding passkeys, restricting to
  the company domain — is done entirely in the Descope console. The docs
  platform picks it up immediately because the flow is rendered by Descope.
</Note>
